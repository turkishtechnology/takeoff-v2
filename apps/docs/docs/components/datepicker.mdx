function ConfirmDemo() {
  const [date, setDate] = React.useState();
  // The panel edits a draft; nothing reaches the field until Apply promotes it.
  // Two values means the hook's single value does not fit — this one is wired
  // by hand.
  const [draft, setDraft] = React.useState();

  return (
    <div className="mx-auto w-72">
      <Field>
        <Field.Label>Appointment</Field.Label>
        <Popover open={open} onOpenChange={toggle}>
          <Input>

              <CalendarIconOutlinedRounded width={20} height={20} />

## Composition

A date picker is built from [`Popover`](/docs/components/popover) and
[`Calendar`](/docs/components/calendar) — **there is no `DatePicker`
component**. Both already own their half of the job: Popover the disclosure,
positioning, dismissal and focus return; Calendar the grid, its keyboard model
and every selection mode. What is left is the join between them, which differs
enough per form that a component would have to guess.

```tsx
<Popover>
  <Popover.Trigger>…</Popover.Trigger>
  <Popover.Content classNames={{ root: 'tk-datepicker-panel' }}>
    <Calendar />
  </Popover.Content>
</Popover>
```

`tk-datepicker-panel` is the one class the design system supplies. Popover's
content box is a text bubble — capped at 296px, with its own padding — so an
unmodified panel clips a calendar. The class lifts the cap, drops the padding,
and removes the calendar's standalone border. It is opt-in because nothing emits
it for you; applying it is what keeps every picker in the system looking the
same.

## With a text input

For a typable field, [`useDatePicker`](#usedatepicker) is the join: it holds the
value, masks the field, turns a completed date into a `Date`, and writes a
picked day back as text. It renders nothing, so every element below is still
yours to place.

Each group is an ordinary object: spread it, override one key of it, or leave it
out. `Input`'s anatomy is untouched — the trigger is just another part, and
order decides placement: anything after the field lands at its inline end, which
is where `Input.ClearButton` already sits. `tk-input-action` is Input's own hook
for a consumer-placed control, so the trigger is that button's twin at every
size rather than a second set of rules that can drift.

## Keyboard

`inputProps.onKeyDown` opens the panel on `ArrowDown`, which is the affordance
that makes the calendar reachable without leaving the keyboard. It is one line
when you wire a field yourself:

```tsx
onKeyDown={event => {
  if (event.key !== 'ArrowDown') return;
  event.preventDefault();
  setOpen(true);
}}
```

Drop it when the field is read-only and the trigger is the only way in. The
panel is not modal: it does not trap focus, and `Escape` or an outside click
dismisses it.

## Localization

A picker has two halves to localize, and they have to agree. The grid takes a
`locale` object from `react-day-picker/locale` — import only the ones you use,
so only those are bundled. The field is the other half: `delimiter` sets both
the separator the mask inserts as you type and the one written back on select,
so `gg.aa.yyyy` is a mask that accepts what the field shows.

<LiveCode
  code={localeDemo}
  noInline
  previewMinHeight={460}
  previewWrapper={ReactSparDemoRoot}
  scope={datePickerScope}
/>

The day order is the field's own convention, not the grid's: `useDatePicker`
writes `dd<delimiter>mm<delimiter>yyyy`, which suits both examples above. A
locale that puts the month first needs `format` as well, and a mask whose
`datePattern` matches it — see [Input](/docs/components/input) for the mask
vocabulary.

`Calendar` carries the rest of the grid's localization: `firstDayOfWeekIndex`
overrides the locale's own first column, `numerals` switches the digit system,
and `dir="rtl"` mirrors the grid. See
[Calendar → Localization](/docs/components/calendar#localization).

## Range across two fields

A range is two values in one panel, so the hook — which owns a single date and
its field text — does not apply. Two fields and one panel is the usual booking
shape: the grid writes back into both.

Spar anchors the panel to its trigger, and there is one `triggerRef` per popover
— so use one trigger and let the other field open the same panel by click,
rather than two triggers where the panel would always hang off whichever mounted
last. The fields are read-only here because the grid owns the selection.

## Apply before committing

`Calendar` commits on the click — `onValueChange` fires the moment a day is
picked, and there is no Apply button to wait for. When the form needs an
explicit confirmation step, hold two values: bind the grid to a draft, and let
the panel's own button promote the draft to the value the field shows. That is
two values again, so this one is wired by hand rather than through the hook.

<LiveCode
  code={confirmDemo}

Re-seeding the draft on open is what makes Cancel — and a dismissal by `Escape`
or an outside click — a plain close: the next open starts from the applied value
again, so an abandoned edit cannot leak into the field. Note the buttons sit
beside the calendar rather than in `Calendar`'s `footer`, which the engine
renders as a live region.

## API Reference

There is no DatePicker component, so there is no component API. What the design
system supplies is one hook and two classes; every other prop comes from the
components the pattern is built out of:

- [Popover](/docs/components/popover) — `open`, `defaultOpen`, `onOpenChange`,
  `side`, `align`, and the dismiss callbacks.
- [Calendar](/docs/components/calendar) — `mode`, `value`, `onValueChange`,
  `month`, `onMonthChange`, `minDate`, `maxDate`, `headerType`, `size`, and the
  rest of the grid surface.
- [Input](/docs/components/input) — the field, its `mask`, and the in-field
  parts.

### useDatePicker {#usedatepicker}

`useDatePicker(options?)` holds the value and the field text for a single-date
picker. It renders nothing and owns no anatomy.

| Option                             | Type                                    | Default        | What it does                                                             |
| ---------------------------------- | --------------------------------------- | -------------- | ------------------------------------------------------------------------ |
| <ApiBadge label="min" />           | <code>Date</code>                       | -              | Earliest selectable date. Bounds the grid **and** the mask.              |
| <ApiBadge label="max" />           | <code>Date</code>                       | -              | Latest selectable date. Bounds the grid **and** the mask.                |
| <ApiBadge label="defaultValue" />  | <code>Date</code>                       | -              | Initial value, uncontrolled.                                             |
| <ApiBadge label="delimiter" />     | <code>string</code>                     | <code>/</code> | Separator between the day, month and year blocks, in the field and mask. |
| <ApiBadge label="format" />        | <code>(value: Date) =&gt; string</code> | `dd/mm/yyyy`   | Renders the picked date into the field.                                  |
| <ApiBadge label="onValueChange" /> | <code>(value?: Date) =&gt; void</code>  | -              | Fires on every change, from either half.                                 |

| Returns                            | Type                                   | What it is                                                                 |
| ---------------------------------- | -------------------------------------- | -------------------------------------------------------------------------- |
| <ApiBadge label="value" />         | <code>Date \| undefined</code>         | The picked date; `undefined` while the field is empty or half-typed.       |
| <ApiBadge label="text" />          | <code>string</code>                    | The field's text, masked.                                                  |
| <ApiBadge label="open" />          | <code>boolean</code>                   | Whether the panel is open.                                                 |
| <ApiBadge label="setValue" />      | <code>(value?: Date) =&gt; void</code> | Drives the picker from outside — a preset, a reset, a restored form value. |
| <ApiBadge label="popoverProps" />  | <code>object</code>                    | `open` / `onOpenChange`, for `Popover`.                                    |
| <ApiBadge label="inputProps" />    | <code>object</code>                    | `mask`, `value`, `onValueChange`, `onKeyDown`, for `Input.Field`.          |
| <ApiBadge label="calendarProps" /> | <code>object</code>                    | `value`, `minDate`, `maxDate`, `onValueChange`, for `Calendar`.            |

### Styling hooks {#datepicker-styling-hooks}

| Class                                    | Applies to        | What it does                                                                                                                                                                                                      |
| ---------------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <ApiBadge label="tk-datepicker-panel" /> | `Popover.Content` | Lifts the bubble's width cap and padding so a calendar fits, and drops the grid's border.                                                                                                                         |
| <ApiBadge label="tk-input-action" />     | `Popover.Trigger` | Owned by [Input](/docs/components/input), not by this pattern — the opt-in hook for any control a consumer places in a field. Makes it `Input.ClearButton`'s twin at every size. Does nothing outside an `Input`. |
