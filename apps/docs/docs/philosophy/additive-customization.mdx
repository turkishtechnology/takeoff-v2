# Additive customization

> Every customization surface is additive. No render-overrides, no escape
> hatches, no upgrade tax.

## The rule

You can **extend** any component — append classes, pass additional HTML
attributes, wrap behaviors — but you cannot **replace** the canonical owner
nodes, their classes, their `data-slot`, or their ARIA wiring.

## Two customization surfaces

### `classNames`

Per-slot class-name overrides. The canonical `tk-*` class stays; your class
appends.

```tsx
<Button
  variant="primary"
  classNames={{
    root: 'ring-2 ring-offset-2',
    label: 'font-mono tracking-wide',
  }}
>
  Check in
</Button>
```

**Rendered root class list:**
`tk-button tk-button--primary ring-2 ring-offset-2`.

### `slotProps`

Per-slot HTML attribute overrides. Canonical ARIA and `data-*` attributes win;
yours fill in anything else.

```tsx
<Button
  variant="primary"
  slotProps={{
    root: { 'data-analytics-id': 'check-in-confirm' },
    spinner: { 'aria-label': 'Processing' },
  }}
>
  Check in
</Button>
```

## What you won't find

- **No `renderIcon` or `renderSpinner` props.** If you want a custom icon, use a
  compound part. If the component doesn't expose one, that's a signal the
  structure isn't meant to be inverted.
- **No `as` prop on leaf components.** Polymorphism lives only where it makes
  sense (e.g., `Button` can render `<button>` or `<a>` depending on `mode`).
- **No unstyled / "headless" escape hatch.** Appearance is owned by the design
  tokens, not by opting out.

## Why

Your customizations are **forward-compatible** by construction. A new `variant`
value next month doesn't break your existing overrides — they target slots and
classes, not structural assumptions.
