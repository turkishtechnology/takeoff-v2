# Spar-shaped surfaces

> Components mirror the structure they represent — not the props a generator
> could invent.

## The rule

A component's public surface should reflect **how it is actually built** — which
owner nodes exist, which slots carry state, which parts render what. Not a
uniform flat prop-bag inferred from an upstream type.

## What that looks like in practice

**Leaf components stay wrapper-first.** `Button` takes `children` and emits the
canonical label slot around them. No `label` prop, no `leftIcon` / `rightIcon`
props, no `renderLabel` override.

```tsx
// ✅ Wrapper-first. children are the label; the wrapper stamps the slot.
<Button variant="primary">Check in</Button>

// ❌ Flat. A content prop pretending the component is leaf-simple.
<Button label="Check in" variant="primary" />
```

**Compound parts are explicit.** `Dialog` exposes `Dialog.Mask`, `Dialog.Panel`,
`Dialog.Header`, `Dialog.Body`, `Dialog.Footer` because those are real
structural owners. You compose them; the wrapper doesn't invent children for
you.

```tsx
<Dialog open={open} onOpenChange={setOpen}>
  <Dialog.Mask />
  <Dialog.Panel>
    <Dialog.Header>
      <Dialog.Title>Online check-in</Dialog.Title>
    </Dialog.Header>
    <Dialog.Body>{/* your content */}</Dialog.Body>
    <Dialog.Footer>{/* your actions */}</Dialog.Footer>
  </Dialog.Panel>
</Dialog>
```

## Why

1. **The DOM stays honest.** Compound parts are real. If the DOM has five nodes,
   the API has five parts.
2. **Your mental model portability is real.** Having used `Dialog`, you can
   predict `Popover`'s shape without reading its docs.
3. **Styling is knowable.** You always know which node carries which class,
   which slot, which `data-*` attribute.

## The counter-example we resist

A well-intentioned `label` or `header` prop is a small compromise that cascades:
soon there's `headerIcon`, `headerActions`, `headerVariant`, and five different
ways to customize the same region. Compound parts stop this before it starts.
